## Problem Statement

**用户的现状**：手里有方法论文档（CONTEXT + 5 ADR），清楚思路，但**没有可运行的代码骨架**。想用框架去优化 A 类目标产物（如某个 SKILL.md、config 文件）时，每一步都要重新设计循环结构、做对隔离、写 ratchet、维护 State——**复用成本极高**。

**真正的痛点**：不是没有方法论，而是**框架的具体形态在 A 类目标域下没固化**。遇到 A 类场景时，Writer / Judge 用什么形态隔离（profile 级而非容器级）、Score 怎么定义、program.md 长什么样、scripts 怎么串联，这些细节每次都要重新决定。

**这个 spec 解决什么**：在方法论指导下，**给出一个 A 类目标域下可立即复用的 v0.1 骨架**——任何 A 类目标产物接到这套骨架上，按规约填配置就能跑通一次完整 Loop。

---

## Solution

**v0.1 交付物是一份「约定 + 最小骨架」**——不是一整套产品。骨架按 ADR-001 实例化机制，**A 类下只实例化核心 4 件**：

| 组件 | A 类实例化状态 | v0.1 交付 |
|---|---|---|
| **Target** | 实例化（核心） | 用户指定 path + git 仓库 |
| **物理隔离** | 实例化（核心） | Writer 和 Judge 作为两个独立 Hermes profile 启动（profile 级隔离，不是容器级） |
| **Ratchet + State** | 实例化（核心） | git ratchet（commit + revert）+ `state/results.tsv` + `state/best_score.txt` |
| **Program 模板** | 实例化（核心） | `templates/program.md.template` + `templates/judge-prompt.md.template` |
| **Worktrees** | **不实例化**（A 类不需要） | git ratchet 隐式承担；v0.2 C 类目标再启用 |
| **Plugins** | **不实例化**（A 类不需要） | v0.2 C 类目标再启用 |
| **Sub-agents 派发** | **不实例化**（A 类不需要） | Writer/Judge 只用两个 profile，不引入 coordinator 派生；v0.2 C 类再启用 |

**运行体验**（一次完整 Loop）：

1. 用户准备 A 类 Target 仓库（git init 过的，含可量化的 hard signal 命令如 `pytest`）
2. 用户填一份 `config.yaml`（指定 Target 路径、Score 维度、Writer/Judge 提示词）
3. 用户跑 `scripts/setup_profiles.sh`（一次性，建 writer / judge 两个 profile）
4. 用户执行 `recursive-tune run --config config.yaml --iterations 10`
5. 每轮迭代：Writer 修改 Target → 对 Target 跑 hard signal → Judge 打分 → 分数上升 commit、下降 revert
6. 结束：用户看 `state/results.tsv` 决定要不要 continue

## User Stories

> 按 to-spec 模板要求铺得广——review 时可以一票否决每一条，不是已承诺要做全部

1. As an A-class framework user, I want a `program.md` template I can copy, so that I can author the agent's task instruction in 10 minutes instead of designing it from scratch.
2. As an A-class framework user, I want a `judge-prompt.md` template, so that the Judge agent gets consistent scoring criteria across iterations.
3. As an A-class framework user, I want to define Score dimensions in a `scoring.yaml` file, so that I can change what "improvement" means without rewriting code.
4. As an A-class framework user, I want Writer and Judge to be **profile-level isolated** (separate Hermes profiles), so that the framework doesn't suffer from the self-evaluation bias at the agent-state level.
5. As an A-class framework user, I want one command to run an entire Loop iteration, so that I can experiment without copy-pasting shell pipelines.
6. As an A-class framework user, I want the framework to commit when score goes up and revert when it goes down, so that I never manually fix a degraded Target.
7. As an A-class framework user, I want a `state/results.tsv` file accumulating every accepted iteration's score, so that I can audit the loop's history.
8. As an A-class framework user, I want commit messages to contain the score delta and a short description, so that `git log` doubles as a progress timeline.
9. As an A-class framework user, I want to set a fixed budget per iteration (e.g. 5 min wall-clock), so that a bad prompt can't burn my entire day.
10. As an A-class framework user, I want dry-run mode that does everything except the actual commit/revert, so that I can sanity-check the wiring before burning budget.
11. As an A-class framework user, I want the framework to invoke my Target's test suite as the hard scoring signal, so that I'm not solely depending on LLM judge.
12. As an A-class framework user, I want Score to be a weighted composition of hard + soft signals, so that improvements on the wrong axis can't game the score.
13. As an A-class framework user, I want the Loop to be parameterized by a single `config.yaml`, so that I can checkpoint different experiments by file copy.
14. As an A-class framework user, I want hard failure when config is incomplete or Target isn't a git repo, so that I fail fast instead of silently no-op.
15. As a framework maintainer, I want clear module interfaces, so that my future work doesn't have to touch the whole skeleton.
16. As a framework maintainer, I want the spec to be reviewable as A-class-only, so that v0.2 C-class extensions don't conflate with v0.1 commitments.
17. As a docs reader, I want docs/ to stay the primary source of truth, so that the code is always derivable from the docs, not the other way around.

> **删除原 User Story #15**（deep-research kanban owner 那条）：v0.1 不绑 deep-research，按 ADR-003 / ADR-003.5 推迟到 v0.2 评估。

## Implementation Decisions

### 决策 D1 — Writer / Judge 隔离：**隔离约定（profile 级，Hermes profile）**

**实施**：
- Writer 和 Judge 各自是一个独立 Hermes profile（`hermes profile create writer` / `hermes profile create judge`）
- **profile 间隔离 state.db + 可见 skills + plugin 加载**，**共享文件系统与 API quota**
- 框架对它们的调用方式：`hermes --profile writer --prompt "<writer-prompt>"` 和 `hermes --profile judge --prompt "<judge-prompt>"`
- **不做的事**：不引入 Docker 容器、不引入独立 Python venv（v0.1 不必要）

**措辞修正（原"物理隔离"措辞降级）**：
- v0.1 范围内，**隔离是 profile 级而非容器级**——共享文件系统、共享 API quota。darwin-skill 字面意义的"物理隔离"在 v0.1 不强制；本框架的"硬规则"是 profile 状态层面互不可见（不同 state.db / 不同 skills 可见集 / 不同 plugin 加载）。术语统一："隔离约定（profile 级）"——见 ADR-001 核心 4 件第 2 件 + CONTEXT.md glossary。
- v0.2 C 类目标（如 deep-research）若需要强隔离，再评估 Docker / 独立 Python venv。

**留口**：`scripts/setup_profiles.sh` 跑一次即可生成两个 profile。

### 决策 D2 — `program.md` 模板格式：**autoresearch + darwin-skill 双源杂交**

**实施**：
- 头部：**任务陈述**（告诉 agent 在改什么 Target、目标是什么）
- 中段：**约束清单**（哪些文件可改、哪些不能动、改动有什么硬边界）
- 尾部：**验证说明**（agent 怎么知道改好了——给硬指标命令 + Judge 关注的信号）
- v0.1 在仓库里提供 `templates/program.md.template`（含 `{{target_path}}` / `{{objective}}` / `{{constraints}}` 占位符）
- `templates/judge-prompt.md.template` 含 `{{target_path}}` / `{{dimensions}}` 占位符；`{{dimensions}}` 由运行脚本从 scoring.yaml 注入 soft 维度。judge 输出 schema（`scores[]`：name / type / score / rationale）行级与 scoring.yaml 维度对齐；`weight` / `signal` 不由 judge 输出——由 scoring.yaml 提供、运行脚本聚合时注入（T1 实现落定，2026-08-12）

**为什么不直接抄 autoresearch 那份**：autoresearch 的 `program.md` 假设 Target 是单一 `train.py`，对配置 / Skill 类 Target 适配差。v0.1 模板刻意做成 A 类目标无感知的占位版。

### 决策 D3 — Score 维度：**hard × soft 加权，9 维为上限**

**实施**：
- `scoring.yaml` schema（v0.1 固定）：
  ```yaml
  dimensions:
    - name: <string>            # 例: test_pass_rate
      type: hard                # 或 soft
      weight: <float 0..1>      # 所有 hard 加权和所有 soft 加权各自归一化
      signal: <command|judge_prompt>
  aggregate:
    hard: arithmetic_mean       # hard 维度内的归约（v0.1 只用均值）
    soft: weighted_mean         # soft 维度内
    final:
      formula: "0.6*hard + 0.4*soft"
      default: true             # 可被 config.yaml 覆盖；A 类纯硬指标场景下
                                # soft 维度为 0 时 60/40 反而稀释硬指标
  ```
- **维度数量软上限 9**（参考 darwin-skill；A 类下 3~5 维最常见），但 v0.1 不强制——A 类目标下 3~5 维最常见

### 决策 D4 — scripts 骨架最小切片：**3 个核心命令 + 1 个配置**

**实施**（A 类实例化集合）：

```
recursive-tune/
├── config.yaml                  # 1 个：用户填的总配置（含 aggregate.final override）
├── scoring.yaml                 # 1 个：Score 维度定义
├── scripts/
│   ├── run_loop.sh              # 1 个：入口，跑 N 次迭代
│   ├── iter.sh                  # 1 个：单次迭代（Writer→Test→Judge→Commit/Revert）
│   └── setup_profiles.sh        # 1 个：建 writer/judge profile
├── templates/
│   ├── program.md.template
│   └── judge-prompt.md.template
└── state/                       # 运行时创建
    ├── results.tsv
    └── best_score.txt
```

**A 类下不实例化**（按 ADR-001）：
- `automations.yaml` 不单列——合并进 `config.yaml` 的 automations 段
- `plugins.yaml` 不列（A 类下 Plugins 组件未实例化）
- `Worktrees` / `Sub-agents 派发`对应文件不存在

**v0.1 不做的事**（Out of Scope 同步移至本段）：不实现跨 Target 复用、不实现分布式、不实现 web UI、不实现自动清理 commit、Plugins 扩展点为 v0.2 范围。

### 决策 D5 — Auth / API 接入：**框架本身无鉴权**

**实施**：
- 框架**不引入任何 API key 管理、不引入登录、不引入 secrets**
- 假设：Writer/Judge profile 在用户已有的 Hermes 配置下能正常工作
- 假设：Target 测试命令（hard signal）能在 user shell 中直接执行
- 唯一限制：脚本跑时硬验证 `git` 可用、`python` 可用

**为什么这样**：本框架是"使用说明书"级别（CONTEXT.md「不是什么」段已声明），不是 agent harness。鉴权层留给下层（Coding Agent / Claude Code / Codex）。

### 决策 D6 — v0.1 验证方式：**假 Target demo**

**实施**：
- v0.1 用**假 Target**（一个内置的小 Python repo + 一个会失败又可以修好的 test）跑通 5 次迭代——**5 是 v0.1 smoke test 数量，非迭代上限**
- 干跑（dry-run）成功、commit 历史干净——证明骨架可用即可
- **v0.1 不指向任何外部 Target**——包括 deep-research（详见 ADR-003 / use-cases/deep-research.md）

> **删除原"骨架可指向 deep-research 仓"措辞**：v0.1 不绑首目标，按 ADR-003.5 严格圈定 A 类目标域，假 Target demo 跑通即视为 v0.1 交付。

### 决策 D7 — 文档 / 代码的角色

- `docs/` **永远是 single source of truth**
- `scripts/` 是 docs 的**可执行投影**——任何脚本逻辑都能在某个 ADR / spec 里找到对应说明
- 新增 / 改任何脚本前，先更 docs，再动代码

### 决策 D8 — 关键 hard rules（写进配置校验）

1. **Target 必须是 git 仓库**（ratchet 前提）
2. **scoring.yaml 至少含 1 个 hard 维度**（防 LLM judge 单一信号把循环带偏）
3. **commit message 必须含 `iter-N: X→Y, ...` 前缀**；具体格式以 autoresearch 参考实现为准、v0.1 implem 决定 schema 细节（X → Y 为数字、description ≤ 80 字符）
4. **分数相等 = 退化 = revert**（ADR-002 关键约束 2）
5. **每轮迭代硬超时**；**默认值固定 5 分钟**，改需写进 `config.yaml` 的 `automations` 段（参考 ADR-001 元素归宿表对"5 分钟固定预算"的归位）
6. **信号完整性规则**：每个 dimension 的 signal 命令必须**有效执行并有输出**（超时 / 输出空 = 缺失），缺失则该 dimension 当次计 0。**与 rule 7 区分**：rule 6 是"信号缺失计 0"，rule 7 是"信号失败 reject"
7. **任一 hard dimension 失败（signal 命令 exit ≠ 0）→ 当次 iteration 直接 reject**，**不计入 final score、不写 results.tsv**——区别于"计 0"，reject 等于这次没跑过
8. **results.tsv = accepted history 的镜像**：记录"成功跑完且 score 被采用"的迭代；rejected iteration **不入 results.tsv、不入 commit message**——`git log` 与 `results.tsv` 保持 accepted-only 一致性，便于审计
9. **默认本地 commit，不自动 `git push`**（呼应 ADR-002 关键约束 1）
10. **Writer 不能看 Judge 本次反馈直到下次 iteration**——每次 iteration 的 Writer 必须仅基于 commit 前一版的 state 工作，避免针对性 score-hacking（darwin-skill 隔离精髓）
11. **Committed state immutable between iterations**：每轮 iteration 开始时，Target 必须先 `git checkout` 到 best commit，ratchet 才能正确生效
12. **meta 层不阻塞 v0.1 first cut**：v0.1 implementation 期间，`docs/` 的 ADR / 模板 / glossary 不必为了满足 ADR-004 meta Score（如 "ADR 模板完整度"、"模板占位符替换成功率"）而调整——meta 验证是 v0.2 范围。拦住"为凑 meta Score 拖慢 A 类骨架交付"的隐性工期耦合（2026-08-11 Opus 4.8 收尾判）

## Testing Decisions

按 handoff §3 提到 scripts 骨架要"跑一次 dry-run"——testing 决策如下：

### T1 — 什么是好测试

**只测外部行为**。v0.1 是 shell + Python 脚本，测试手段按层：
- **shell 脚本**：跑一遍 happy path，断言 exit code 和 `state/` 文件写入
- **Python 核心逻辑**（ratchet/state）：用 pytest 写单元测，但只测"score 比较 / commit message 格式化 / results.tsv 追加"这几种纯函数
- **不测**：不测 LLM 输出内容（不可重现）、不测 Writer 实际编辑结果（是 agent 的活）

### T2 — 测试模块

| 模块 | 测试手段 | 优先级 |
|---|---|---|
| `iter.sh` 流程编排 | shell 集成测试（用假 Target，验证 5 轮迭代 commit/revert 正确） | P0 |
| `setup_profiles.sh` | shell 集成测试（验证两个 profile 创建成功） | P0 |
| 配置校验（缺硬维度、results.tsv reject 路径） | pytest 单元测 | P1 |
| `scoring.yaml` 解析 | pytest 单元测 | P1 |
| templates 占位符替换 | pytest 单元测（`tests/test_templates.py`：占位符集合 / 替换无残留 / D2 三段顺序 / A 类无感知词表） | P2 |
| `results.tsv` 追加（仅记 accepted iteration） | pytest 单元测 | P1 |

### T3 — Prior art

仓库当前零代码——没有 prior art 可参考。v0.1 自身会成为后续版本的 prior art。

### T4 — 端到端验证

v0.1 必须配一个**假 Target demo**（一个 Python 仓库 + 一个会失败又可以修好的 test），确保：
- `iter.sh` 能在真 git 仓库上工作
- ratchet 行为（升 commit / 降 revert）符合 ADR-002
- `state/results.tsv` 累计 ≥ 1 行（依 D8 hard rule 8：仅记 accepted iteration）
- 5 次迭代里至少 1 次 hard dimension 失败 → 触发 reject 路径（D8 hard rule 7），验证 results.tsv 该次不入表

## Out of Scope

明确**不做**的事（避免 scope creep）：

1. **不实现 deep-research kanban 的真实改造**——ADR-003 已推迟到 v0.2 评估
2. **不实现 v0.1 范围外的扩展 3 件**（Worktrees / Plugins / Sub-agents 派发）——A 类不实例化；**v0.1 不为扩展件预留任何目录 / 文件 / 配置项 stub**
3. **不写 web UI / dashboard**——CLI 跑通就够
4. **不实现自动清理 commit 历史**——commit 爆炸留 v0.2+ 处理
5. **不引入 Docker 容器级隔离**——profile 级隔离已够
6. **不做分布式 / 并行 writer**——单 writer 串行足够
7. **不做 Target 自动发现**——每次手动指定 Target 路径
8. **不写 spec 校验工具**（如自动检查 6 段模板完整性）——人工 review 就够
9. **不做 v0.1 范围内的 meta 层可执行骨架**——ADR-004 文档级承诺已落地；meta 可执行骨架 v0.2
10. **不做 Plugins 扩展点**——A 类下 Plugins 未实例化；v0.2 再启用
