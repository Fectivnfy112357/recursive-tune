# v0.1 Skeleton Spec · recursive-tune

> 状态：提议（2026-08-11，grill 第一轮收口后由 to-spec 生成）
> 关联：CONTEXT.md · ADR-001（骨架）· ADR-002（ratchet）· ADR-003（首目标）
> 用途：把 grill 收口的决策压成可构建的计划。本 spec 是 `/to-tickets` 的直接输入，不是 GH issue 本体。
> 范围：本 spec 只覆盖 **v0.1 最小可执行骨架**——能「dry-run 跑通一次完整 Loop」就视为达成。

---

## Problem Statement

**用户的现状**：手里有 3 份方法论文档（CONTEXT + 3 ADR），清楚思路，但**没有可运行的代码骨架**。想用框架去优化某个目标产物（如 deep-research kanban）时，每一步都要重新设计循环结构、做对隔离、写 ratchet、维护 State——**复用成本极高**。

**真正的痛点**：不是没有方法论，而是**框架的具体形态没固化**——遇到真实场景时，Writer / Judge 用什么形态隔离、Score 怎么定义、program.md 长什么样、scripts 怎么串联，这些细节每次都要重新决定。

**这个 spec 解决什么**：在方法论指导下，**给出一个可立即复用的 v0.1 骨架**——任何目标产物接到这套骨架上，按规约填配置就能跑通一次完整 Loop。

---

## Solution

**v0.1 交付物是一份「约定 + 最小骨架」**——不是一整套产品。骨架由 6 件套（ADR-001）组成，但 v0.1 每件只交付**最小可执行切片**：

| 组件 | v0.1 交付 |
|---|---|
| **Automations** | 一份 YAML 配置（`automations.yaml`）+ 一个调度入口（`scripts/run_loop.sh`） |
| **Worktrees** | 由 git ratchet 隐式承担，v0.1 不另实现 |
| **Skills** | 一份 `program.md` 模板 + `judge-prompt.md` 模板（可参数化） |
| **Plugins** | 一份 plugin 清单（`plugins.yaml`）—— v0.1 是空壳结构，不要求预置插件 |
| **Sub-agents** | Writer 和 Judge 作为两个**独立 agent profile** 启动（通过 Hermes `hermes profile` 隔离） |
| **State** | `state/results.tsv` + `state/best_score.txt` + `state/program.md`（ratchet 隐式） |

**运行体验**（一次完整 Loop）：

1. 用户准备 Target 仓库（git init 过的）和 Target 文件
2. 用户填一份 `config.yaml`（指定 Target 路径、Score 维度、Writer/Judge 提示词）
3. 执行 `recursive-tune run --config config.yaml --iterations 10`
4. 每轮迭代：Writer 修改 Target → 对 Target 跑测试/评测 → Judge 打分 → 分数上升 commit、下降 revert
5. 结束：用户看 `state/results.tsv` 决定要不要 continue

## User Stories

> 按 to-spec 模板要求铺得广——目标是让你在 review 时能一票否决每一条，不是已承诺要做全部

1. As a framework user, I want a `program.md` template I can copy, so that I can author the agent's task instruction in 10 minutes instead of designing it from scratch.
2. As a framework user, I want a `judge-prompt.md` template, so that the Judge agent gets consistent scoring criteria across iterations.
3. As a framework user, I want to define Score dimensions in a `scoring.yaml` file, so that I can change what "improvement" means without rewriting code.
4. As a framework user, I want Writer and Judge to be physically isolated (separate agent profiles), so that the framework doesn't suffer from the self-evaluation bias.
5. As a framework user, I want one command to run an entire Loop iteration, so that I can experiment without copy-pasting shell pipelines.
6. As a framework user, I want the framework to commit when score goes up and revert when it goes down, so that I never manually fix a degraded Target.
7. As a framework user, I want a `state/results.tsv` file accumulating every iteration's score, so that I can audit the loop's history.
8. As a framework user, I want commit messages to contain the score delta and a short description, so that `git log` doubles as a progress timeline.
9. As a framework user, I want to set a fixed budget per iteration (e.g. 5 min wall-clock), so that a bad prompt can't burn my entire day.
10. As a framework user, I want dry-run mode that does everything except the actual commit/revert, so that I can sanity-check the wiring before burning budget.
11. As a framework user, I want the framework to invoke my Target's test suite as the hard scoring signal, so that I'm not solely depending on LLM judge.
12. As a framework user, I want Score to be a weighted composition of hard + soft signals, so that improvements on the wrong axis can't game the score.
13. As a framework user, I want the Loop to be parameterized by a single `config.yaml`, so that I can checkpoint different experiments by file copy.
14. As a framework user, I want to write plugins that hook into pre/post writer and judge, so that I can add logging / notifications without forking the core.
15. As a deep-research kanban owner, I want the framework to be able to point at my existing kanban repo, so that I can run a Loop on my current optimization candidates without rewriting anything.
16. As a framework maintainer, I want clear module interfaces, so that my future work doesn't have to touch the whole skeleton.
17. As a framework user, I want hard failure when config is incomplete or Target isn't a git repo, so that I fail fast instead of silently no-op.
18. As a framework user, I want docs/ to stay the primary source of truth, so that the code is always derivable from the docs, not the other way around.

## Implementation Decisions

### 决策 D1 — Writer / Judge 物理隔离：**独立 Hermes profile**

**提议**（须 review 拍板）：
- Writer 和 Judge 各自是一个独立 Hermes profile（`hermes profile create writer` / `hermes profile create judge`）
- 隔离方式：不同 profile = 不同 `~/.agents/skills/` 可见集 + 不同 plugin 加载 + 不同 `state.db`
- 框架对它们的调用方式：`hermes --profile writer --prompt "<writer-prompt>"` 和 `hermes --profile judge --prompt "<judge-prompt>"`
- **不做的事**：不引入 Docker 容器、不引入独立 Python venv（v0.1 不必要）

**为什么这样**：darwin-skill 的核心要点就是物理隔离——profile 是 Hermes 已经原生支持的、最轻量的隔离单元。用户已经在用 profiles（memory 里看到）——这是已有工具复用，不是新发明。

**留口**：v0.1 要把「writer/judge profile 怎么建」写成 `scripts/setup_profiles.sh`，跑一次即可生成。

### 决策 D2 — `program.md` 模板格式：**基于 autoresresearch + darwin-skill 双源杂交**

**提议**：
- 头部：**任务陈述**（告诉 agent 在改什么 Target、目标是什么）
- 中段：**约束清单**（哪些文件可改、哪些不能动、改动有什么硬边界）
- 尾部：**验证说明**（agent 怎么知道改好了——给硬指标命令 + Judge 关注的信号）
- v0.1 在仓库里提供 `templates/program.md.template`（含 `{{target_path}}` / `{{objective}}` / `{{constraints}}` 占位符）

**为什么不直接抄 autoresresearch 那份**：autoresearch 的 `program.md` 假设 Target 是单一 `train.py`，对配置 / Skill 类 Target 适配差。v0.1 模板刻意做成「目标无感知」的占位版。

### 决策 D3 — Score 维度：**hard × soft 加权，9 维为上限**

**提议**：
- `scoring.yaml` schema（v0.1 固定）：
  ```yaml
  dimensions:
    - name: <string>            # 例: test_pass_rate
      type: hard                # 或 soft
      weight: <float 0..1>      # 所有 hard 加权和所有 soft 加权各自归一化
      signal: <command|judge_prompt>
  aggregate:
    hard: arithmetic_mean       # hard 维度内的归约（v0.1 只用均值）
    soft: weighted_mean         # soft 维度内
    final: 0.6*hard + 0.4*soft  # 最终分（v0.1 默认 60/40）
  ```
- **维度数量软上限 9**（沿用 darwin-skill），但 v0.1 不强制——3~5 维最常见
- **硬指标 ≥ 1 维**：每个 Score 至少要有 1 个 hard 维度，否则配置校验失败（hard rule，防 LLM judge 单一信号把循环带偏）

### 决策 D4 — scripts 骨架最小切片：**3 个核心命令 + 1 个配置**

**提议**（最小可执行集合）：

```
recursive-tune/
├── config.yaml                  # 1 个：用户填的总配置
├── scripts/
│   ├── run_loop.sh              # 1 个：入口，跑 N 次迭代
│   ├── iter.sh                  # 1 个：单次迭代（Writer→Test→Judge→Commit/Revert）
│   └── setup_profiles.sh        # 1 个：建 writer/judge profile
├── templates/
│   ├── program.md.template
│   └── judge-prompt.md.template
└── state/                       # 运行时创建
    ├── results.tsv
    └── best_score.txt
```

**v0.1 不做的事**：不实现跨 Target 复用管理、不实现分布式、不实现 web UI、不实现自动清理 commit。

### 决策 D5 — Auth / API 接入：**框架本身无鉴权，依赖运行环境**

**提议**：
- 框架**不引入任何 API key 管理、不引入登录、不引入 secrets**
- 假设：Writer/Judge profile 在用户已有的 Hermes 配置下能正常工作
- 假设：Target 测试命令（hard 信号）能在 user shell 中直接执行
- 唯一限制：脚本跑时硬验证 `git` 可用、`python` 可用（v0.1 用 Python 写核心逻辑）

**为什么这样**：本框架是「使用说明书」级别（CONTEXT.md 「不是什么」段已声明），不是 agent harness。鉴权层应留给下层（Coding Agent / Claude Code / Codex）。

### 决策 D6 — 第一个真实目标的入口：**deep-research kanban 诊断，不动现状**

直接照搬 ADR-003：v0.1 不实现 deep-research 任何改造，仅保证骨架**可以**指向 deep-research 仓（`C:\Users\32115\AppData\Local\hermes\docs\deep-research\`）跑诊断。

**v0.1 验证方式**：用一份"假 Target"（一个内置的小 demo repository）跑通 5 次迭代、干跑成功、commit 历史干净——证明骨架可用即可。deep-research 真上车是 v0.2 之后的事。

### 决策 D7 — 文档 / 代码的角色

- `docs/` **永远是 single source of truth**
- `scripts/` 是 docs 的**可执行投影**——任何脚本逻辑都能在某个 ADR / spec 里找到对应说明
- 新增 / 改任何脚本前，先更 docs，再动代码

### 决策 D8 — 关键 hard rules（写进配置校验）

1. **Target 必须是 git 仓库**（ratchet 前提）
2. **scoring.yaml 至少含 1 个 hard 维度**
3. **commit message 必须含 `iter-N: X→Y, ...` 前缀**
4. **分数相等 = 退化 = revert**（ADR-002 关键约束 2）
5. **每轮迭代硬超时**（默认 5 分钟，可配）

## Testing Decisions

按 handoff §3 提到 scripts 骨架要 "跑一次 dry-run"——testing 决策如下：

### T1 — 什么是好测试

**只测外部行为**。v0.1 是 shell + Python 脚本，测试手段按层：
- **shell 脚本**：跑一遍 happy path，断言 exit code 和 `state/` 文件写入
- **Python 核心逻辑**（ratchet/state）：用 pytest 写单元测，但只测「score 比较」「commit message 格式化」「results.tsv 追加」这几种纯函数
- **不测**：不测 LLM 输出内容（不可重现）、不测 Writer 实际编辑结果（是 agent 的活）

### T2 — 测试模块

| 模块 | 测试手段 | 优先级 |
|---|---|---|
| `iter.sh` 流程编排 | shell 集成测试（用假 Target，验证 5 轮迭代 commit/revert 正确） | P0 |
| `setup_profiles.sh` | shell 集成测试（验证两个 profile 创建成功） | P0 |
| 配置校验（缺硬维度等） | pytest 单元测 | P1 |
| `scoring.yaml` 解析 | pytest 单元测 | P1 |
| templates 占位符替换 | pytest 单元测 | P2 |
| `results.tsv` 追加 | pytest 单元测 | P1 |

### T3 — Prior art

仓库当前零代码——没有 prior art 可参考。v0.1 自身会成为后续版本的 prior art。

### T4 — 端到端验证

v0.1 必须配一个**假 Target demo**（一个 Python 仓库 + 一个会失败又可以修好的 test），确保：
- `iter.sh` 能在真 git 仓库上工作
- ratchet 行为（升 commit / 降 revert）符合 ADR-002
- `state/results.tsv` 累计 5 行，score 从 baseline 提升到 ≥ 某个数字

## Out of Scope

明确**不做**的事（避免 scope creep）：

1. **不实现 deep-research kanban 的真实改造**——ADR-003 已声明，第一阶段只诊断
2. **不写 web UI / dashboard**——CLI 跑通就够
3. **不实现自动清理 commit 历史**——commit 爆炸留 v0.2+ 处理
4. **不引入 Docker 隔离**——profile 已够
5. **不做分布式 / 并行 writer**——单 writer 串行足够
6. **不做 Target 自动发现**——每次手动指定 Target 路径
7. **不写 spec 校验工具**（如自动检查 6 段模板完整性）——人工 review 就够
8. **不实现 deep-research 历史文件的自动引用**——用户手动 link 即可
9. **不做自我修改框架本身**（meta 递归的第二层暂缓到 v0.3+）
