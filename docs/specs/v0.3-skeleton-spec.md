## Problem Statement

v0.2 first cut 验证的是"fixture 下自洽",**不是**"真实 C 类多 agent 流水线能跑"。三处裂缝:Sub-agents 派发只有接口无实现(v0.2 D5 字段层落实未知);真实 C 类任务零证据(T4 e2e 是 fake hermes + fixture);meta 层落地条件不明(v0.2 OOS 项触发条件是"首批数据",meta_check.sh 才跑过一次)。

## Solution

v0.3 first cut 交付三件事:

1. **Sub-agents 派发骨架件**——落实 v0.2 D5 接口字段层:coordinator spawn 子 agent、按 recipe 分工、聚合结果进 ratchet、回报信封。
2. **1 个真实 C 类任务** = 3 agent 多语种化 PR 流水线(真实 GitHub 仓库 README;agent = 翻译 + 一致性自检 + PR 起草;产出 PR 可人工 merge;recipe 可二次执行且二次 wall clock ≤ 首次 50%)。
3. **必入约束 3 件不允许**:断点续跑(v0.4 再说)/ 5 agent 划分(v0.3 恰好 3 agent,≠3 一律报错)/ 独立 glossary 持久化件(走 recipe 内文件级约定,不另起骨架件)。

## User Stories

1. As a v0.3 framework user running a multi-agent pipeline, I want the Sub-agents dispatch to spawn per-recipe agents (translation / consistency-check / PR-draft) and aggregate their state into a single PR, so that C-class actually executes rather than is described.
2. As a v0.3 framework user, I want re-runnable recipes whose second-run wall clock median is ≤50% of the first (via per-agent `cacheable` reuse, D1), so that recipe is the unit of reuse.
3. As a v0.3 framework user, I want agent failures to result in a clean from-scratch re-run (no checkpoint resume), so that v0.3 scope stays honest about its limits.
4. As a v0.3 framework user, I want glossary terms shared via recipe-level file paths (not a new framework component), so that cross-agent terminology consistency is a task convention.
5. As a v0.3 framework maintainer, I want the Sub-agents 字段层 defined for the first time in v0.3 — 输入 / 输出 / 状态 / 依赖四元组对应 v0.2 D5 接口规格,v0.3 不复制 v0.2 D5 写法 — so that D5 stops being a paper interface.

## Implementation Decisions

### D1 · Sub-agents 派发骨架件

- 落实 v0.2 D5 接口字段层(v0.2 D5 第 3 条留口,v0.3 首次填):coordinator 按 recipe spawn 子 agent,各持独立 profile(来自 v0.2),产出回写各自 output_path;骨架件只负责 spawn / dispatch / aggregate,不规定协作模式。
- **ratchet 写入语义**:coordinator 聚合结果按 v0.2 D5 第 3 条"子 agent 结果聚合进 ratchet"落地——聚合产物经 ratchet 提交(复用 ADR-002),不是泛称的"写共享 state";子 agent 中间产物只落 state,不单独进 ratchet。
- 接口边界:recipe 文件(任务约定)规定 agent 列表 / prompt 模板 / 协作顺序 / state 读写路径 / 各 agent 的 cacheable 标记。
- **触发引用(ADR-005 决策 1 第 3 行原话)**:Sub-agents 触发 = coordinator 派生子 agent 协同工作(多 agent 流水线)且子 agent 间需要明确分工 + 状态共享——v0.3 C 类任务命中。
- **Worktrees 是否命中(正面回应 ADR-005"三件 C 类必装"口径)**:判据是"并行分支间共享 Target 路径会冲突"。3 agent 各写 README **不同 section** → 不共享 Target 路径 → Worktrees 不命中;若 3 agent 写同一文件同一区域 → 命中 → 该轮必装。v0.3 first cut **选"3 agent 写不同 section"**,故 **v0.3 first cut 只启用 Sub-agents 一件,Worktrees / Plugins 触发未命中,v0.4+ 再评估**(非否决 C 类必装,是本轮 recipe 设计使其未触发)。
- **recipe 复用机制(50% 判据的实现来源)**:
  - recipe 每个 agent 必须标 `cacheable: true|false`;`no_cache` 的 agent 每轮必跑。
  - 二次执行时,coordinator 对 `cacheable` 且 `output_path` 已存在且上游输入未变的 agent **直接复用输出,不 spawn**。
  - 计时边界:**不含** clone / PR 提交,**含** LLM call + agent 内部 IO。
  - 阈值可执行式:同一 recipe 首次跑 3 次得 time_1a/1b/1c、二次跑 3 次得 time_2*,判据 = `median(time_2*) ≤ median(time_1a, time_1b, time_1c) × 0.5`。

### D1.5 · Sub-agents 接口最小 schema(字段层)

- **recipe 字段**:`agents[].name`(唯一)/ `.profile`(v0.2 隔离 profile 名)/ `.prompt_path` / `.state_rw`(读写路径列表)/ `.cacheable`;`agents` 长度必须 = 3(见 D2)。
- **spawn 返回信封**:`{ agent, status, output_path, duration_ms, error_code }`;`status ∈ {ok, failed, cached}`;`error_code` 在 `status=ok|cached` 时为 null。
- **错误码(≥3 起步)**:`E_AGENT_FAIL`(子 agent 非零退出 / 无产物)、`E_RECIPE_INVALID`(schema 不合法:空 recipe / 缺字段 / 重复 name / agents 长度 ≠ 3)、`E_STATE_RACE`(两 agent 并发写同一 state 路径)。
- **原子性**:聚合失败 = **不落 state、不动 ratchet**(与 D2"从头跑"一致,无中间态可续)。
- 落地:骨架件脚本路径与模块名 first cut 锁定(spec 不锁扩展名,沿用 v0.2 D9 rule 写法)。

### D2 · 真实 C 类任务 = 3 agent 多语种化 PR 流水线

- 任务对象:真实 GitHub 仓库 README(候选:v0.2 自己或同档开源项目,first cut 周内锁定);3 agent 各负责 README **不同 section**(见 D1 Worktrees 判据)。
- **恰好 3 agent**(`agents` 长度 ≠ 3 → `E_RECIPE_INVALID` 报错,既不许扩 5 也不许缩 2):翻译(主流程 + 术语提取)/ 一致性自检(独立验证)/ PR 起草(收尾组装)。
- **不引入**新骨架件:隔离 profile 来自 v0.2 / glossary 读写路径走 recipe 约定 / 持久化 state 来自 v0.2 / ratchet 复用 ADR-002。
- 完成判定三项齐备:**T2a 机械结构通过**(stub 下 spawn 顺序 / 聚合写入 / PR 结构)+ **T2b 一次真实 e2e 证据**(真实 LLM + 真实仓库,PR 链接落 `docs/handoff/v0.3-real-e2e-evidence.md`)+ **同一 recipe 连跑 2 次,二次 wall clock 中位 ≤ 首次中位 × 50%**(计时边界见 D1)。
- 任一 agent 失败 → 从头跑(v0.3 显式让步,断点续跑不在 v0.3 范围;聚合失败不落 state,见 D1.5 原子性)。

### D3 · meta 层与 v0.2 OOS 项处置

- **D3.1 过程(v0.3 做)**:meta 层走共生,Glossary 静态化按需就地补(哪里卡术语、哪里跨 profile 出入,补一条);v0.3 任务跑通后 `meta_check.sh` 再跑一次,记录 **n=2** 运行数据。
- **D3.2 触发量化**:v0.2 OOS 所称"首批数据"定义为 **n ≥ 10 次 meta_check.sh 运行,且覆盖 ≥5 个 ADR + ≥3 个模板**;n=2 明确**不构成**首批数据。
- **D3.3 落地**:D3.2 达成后才起单独 ADR(ADR-004 Open Issue / CONTEXT §TODO 6 的承接)——按 v0.3 的 n=2 速率,第 1 个 ADR 触发预计在 v0.4 准备,v0.3 内不开 ADR。
- 不进 v0.3:CI 接入 / profile vs 容器隔离术语加固 / 隔离升级 Docker / 5 agent 划分 / Worktrees & Plugins 字段层 / A 类目标域上车。

### D4 · v0.3 C 类任务的 scoring 维度与 hard signal

- 三维(全 hard,命令可量化):**翻译覆盖度** ≥95% 段落 / **术语一致性** glossary 关键词命中率 ≥90% / **PR 结构合法** lint pass。
- hard signal 来源:覆盖度 = 命令比对原文段落数 vs 译文段落数(machine 计);术语一致性 = grep glossary 关键词在译文中的出现率;PR 结构 = `gh pr diff --stat` 不报错。三条均走 v0.2 D3 三段式封装进 `signal` 字符串。
- **fixture 不适用**:C 类产物非固定答案,无法构造 ≥10 positive + ≥10 negative 的 ground truth;v0.3 用上述命令型硬指标替代 D9 fixture 门,形式化留 OOS(触发时机见 OOS 段)。

## Testing Decisions + Out of Scope

### Testing Decisions

- **T1 · Sub-agents 单元测试**:coordinator spawn 正确性、state 聚合原子性、recipe 解析鲁棒性(空 recipe / 缺 agent 字段 / 重复 agent 名 / agents 长度 ≠ 3);另加三条字段层断言:
  - (a) spawn 返回信封结构:`{agent, status, output_path, duration_ms, error_code}` 五字段齐备,`status ∈ {ok, failed, cached}`
  - (b) 错误码映射:子 agent 非零退出 → `E_AGENT_FAIL`;schema 不合法 → `E_RECIPE_INVALID`;并发写同一 state 路径 → `E_STATE_RACE`
  - (c) 聚合失败 → state 目录无新增文件、ratchet HEAD 未动(D1.5 原子性)
- **T2a · 3 agent 机械结构 e2e**(CI 跑,LLM call 走 fake hermes stub,与 v0.2 T4 模式一致):spawn 顺序符合 recipe 声明的协作顺序;各 agent 产物按 `state_rw` 写入正确路径且被 coordinator 聚合;产出 PR **结构**正确(标题非空 / 正文含三 agent 段落 / 文件 diff 形态为 README 修改)——**只验结构,不验译文内容**。二次执行 cache 复用生效(`status=cached` 的 agent 数 > 0),并按 D1 计时式断言 `median(time_2*) ≤ median(time_1*) × 0.5`(各跑 3 次)。
- **T2b · 真实 e2e 证据**(手工 1 次,非 CI):真实 LLM + 真实 GitHub 仓库跑通 1 次,产出可人工 merge 的 PR;PR 链接与两次 wall clock 数据记入 `docs/handoff/v0.3-real-e2e-evidence.md`。"PR 可人工 merge""wall clock ≤50%"两条判据**只在 T2b 下成立**,不作为 CI 断言。
- **T3 · 必入约束回归守护**:任一 PR 不得引入断点续跑代码路径、不得新增独立 glossary 持久化件;agent 数守护改为可执行断言——(a) recipe validator 单元测试:`agents` 长度 ≠ 3 → fail 且 `error_code = E_RECIPE_INVALID`;(b) 扫描 repo 内所有示例 recipe 文件,断言 `len(agents) == 3`(不做源码 grep "5 agent")。

### OOS 占位机制(v0.5 首用)

**约束**: 延期项必须配: 触发事件(具名非类别词) / 占位桩函数 / 关闭 owner; 不允许裸延期。示范桩见 `tests/fixtures/d9_placeholder.py`。

### Out of Scope(v0.3 不做)

- Worktrees & Plugins 字段层实现——本轮 recipe 设计使触发未命中(见 D1),v0.4+ 再评估。
- **C 类 D9/Q5 fixture 形式化**:v0.3 first cut 用 D4 命令型硬指标代替;触发 = v0.4 撞真实 C 类任务需要跨任务可比的 ground truth 时才形式化。
- **`scoring.yaml.template`(v0.2 D4 点名"v0.3 再补")**:v0.3 不补;触发 = v0.4 撞更多 scoring 维度时。
- **`iter.sh` signal array token 化(v0.2 D3 选项 c,点名"v0.3+ 实施")**:v0.3 不动,继续用选项 (a) staging 短路径;触发 = v0.4 撞 token 化失败时。
- **O5 exempt 升级为 scoring.yaml exempt flag(v0.2 D1 候选 a)**:v0.3 不实现;触发 = v0.3 跑通后用户带入新 hard signal 需项目级配置化时。
