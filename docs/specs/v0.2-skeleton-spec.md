# v0.2 Skeleton Spec · A 类文本 Target hard signal + meta 两维 hard + 扩展 3 件接口

> 状态：v0.2 启动 spec 草稿 v2（2026-08-12，v0.1 收尾后起草；v1 经 fresh 审阅修订）
> 性质：v0.2 first cut 的构建契约（对应 v0.1 的 `docs/specs/v0.1-skeleton-spec.md`）
> 上游：ADR-005（范围锚定 + 优先级 + 明确缓议）、`docs/use-cases/text-target-hard-signal.md`（D9 依据）、`scripts/meta_check.sh`（已落）
> 版本锚：v0.2 = A 类文本 Target 真实战场 + meta 两维 hard 落地 + 扩展 3 件接口定义（C 类不上车）

---

## Problem Statement

v0.1 跑通证明的是"骨架能承载 autoresearch 原生代码型场景"（`pytest -q` 社区共识），**不是**"骨架能承载 A 类真实战场"（SKILL.md / prompt 文本 Target）——fresh audit §保留 1 的判定。具体裂缝：

1. **文本型 Target 的 hard signal 无准入判据**：`scoring.yaml` 的 `signal` 字段只接命令字符串，但"命令的 ground truth 从哪来、false positive 率怎么测"完全开放——没有判据，任何命令都可以声称是 hard signal，循环退化为纯 soft（违反 D8 rule 2 精神）。
2. **meta 层承诺未落地**：ADR-004 写了 meta Score 契约，但 v0.1 三件事打包顺延（D8 rule 12 副作用）——"ADR 完整度"和"模板占位符替换"两维 hard 其实已具备跑通条件，从未跑过。
3. **扩展 3 件只有归位没有启用条件**：ADR-001 定义了 4+3 骨架，但 Worktrees / Plugins / Sub-agents 何时上车没有 trigger 判定依据。

## Solution

v0.2 first cut 交付三件事：

1. **D9 rule（fixture-set 验证）**——任何 `type: hard` 的 dimension 必须先有已知 baseline + 反例集（≥10 positive + ≥10 negative），在 fixture-set 上跑过且 positive/negative ≥ 80% 才可标 hard；不通过 = `validate_config.py` 提示降级为 soft（不 exit 1 阻断，由用户确认）。Q5 是 hard/soft 的通用分界线，不只限于文本型 Target。
2. **meta 两维 hard 落地**——`scripts/meta_check.sh`（ADR 模板完整度 + 模板占位符替换成功率）作为 ADR-004 meta 层第一步；复用 v0.1 已落骨架，不另起 CI。
3. **扩展 3 件接口定义**——以 ADR-005 决策 1 trigger 矩阵为输入，定义三件在 C 类上车时的接口契约（只定义，不实现；A 类必不装）。

## User Stories

**A 类文本 Target 用户：**

1. As a v0.2 framework user optimizing a SKILL.md, I want `validate_config.py` at config time to check that my hard signal command has passed fixture-set validation, so that I know my score is measuring signal, not noise.
2. As a v0.2 framework user, I want a hard dimension that fails fixture-set validation to be offered a soft downgrade rather than blocking loop startup, so that I can still run my loop while I improve the signal.
3. As a v0.2 framework user, I want `validate_config.py` to report which hard dimensions lack fixture-sets, so that I can see at config time what will not pass the D9 gate.
4. As a v0.2 framework user, I want the fixture-set format to be simple to author by hand (expected ~YAML list of {input, expect: pass|fail}, exact format locked at first real run), so that I can create it without tooling.
5. As a v0.2 framework user, I want my text-target hard signal command to be a three-part command (eval-set-path + runner + parser) encapsulated in the signal string, so that iter.sh and validate_config.py do not need to understand its internals.
6. As a v0.2 framework user, I want parser failures to resolve via existing D8 rule 6/7 semantics (empty output → 0, non-zero exit → reject), so that there is no third scoring state to reason about.
7. As a v0.2 framework user with a SKILL.md target, I want to run the skeleton loop for 3 iterations end-to-end against the text target, so that I can verify the text-target path works in the real workflow (not just the code demo).

**meta 层维护者：**

8. As a framework maintainer, I want one command that checks both ADR completeness and template placeholder replacement, reusing v0.1 assets, tolerating missing state with a warning, and exposing --json / --strict, so that meta layer progress is observable without a new CI stack.
9. As a framework maintainer, I want ADR completeness checks to exempt known non-standard ADRs via a small table (current 1 entry), so that the check reflects the actual template without hardcoding every file.

**C 类探索者（multi-agent 流水线上车评估）：**

10. As a v0.2 framework user exploring C-class, I want the Worktrees trigger to be defined (parallel branch exploration when single-writer serial is insufficient and shared Target paths conflict), so that I can judge when to enable it.
11. As a v0.2 framework user exploring C-class, I want the Plugins trigger to be defined (external hook / adapter when config-only switching can't match change frequency), so that I can judge when provider switching needs an abstraction.
12. As a v0.2 framework user exploring C-class, I want the Sub-agents dispatch interface to be defined (coordinator spawning child agents with division of labor + state aggregation), so that I know what the interface contract will be.
13. As a v0.2 framework user exploring C-class, I want to know how Q5 fixture-set validation applies to multi-agent targets (what ground truth looks like when output is a coordinated product), so that the D9 gate doesn't silently break in C-class.

## Implementation Decisions

### D1 · D9 rule（fixture-set 验证，Q5 升格为通用判据）

- 任何 `type: hard` 的 dimension 在 `validate_config.py` 校验时必须有 fixture-set 证据（`fixtures/<dimension-name>.yaml` ≥ 20 条样本：≥10 positive + ≥10 negative）。
- 验证：signal 命令在 fixture-set 上跑一遍，positive ≥ 80% 命中 + negative ≥ 80% 正确排除。**两条独立阈值**：数量门槛（≥20 条）与执行命中门槛（≥80%），分别判定。
- 不通过 = 提示降级为 soft（由用户决定），**不 exit 1 阻断**（信号在长尾上不够稳是常态，直接拒绝用户太严）。
- 豁免：社区共识 hard signal（v0.1 demo 用过的 `pytest -q` 等）首次使用免跑；用户自行构造的代码型命令仍需 Q5。**豁免识别机制在 v0.2 first cut 第 1 周工单里锁**：候选 (a) scoring.yaml 加 exempt flag；(b) `validate_config.py --known-hard-list` 临时白名单；候选歧义留 O5。
  - **O5 锁定（v0.2.1 commit 锁）**：采用候选 (b) 的代码内化版本——`scripts/validate_config.py:33` 的 `KNOWN_EXEMPT_COMMANDS = ("pytest",)` 内建常量，无 CLI 暴露；新增加白名单需改代码 + 同步 `tests/test_d9_gate.py` 加 `test_exempt_xxx_variants` 测试。
  - **升级到 scoring.yaml exempt flag（候选 a）的判定**：当白名单需要被项目层配置化（即不同 Target 仓库有不同的"社区共识"集合）时触发——v0.2.1 first cut 用代码常量足够（pytest 共识跨域一致），项目级配置化是 v0.3+ 再评估的扩展（明确缓议，不预留 stub）。
- **D9 落地位置**：`validate_config.py` 当前零 D9 检查——D9 落地工单 = v0.2 first cut 第 1 周 ticket，与 T1（D9 校验测试）同步推进。
- fixture-set 是信号的 ground truth，不是 Target 的 ground truth。

### D9 执行机制 · signal 命令 D9 模式约定（A-min）

- `validate_config.py` 执行 signal 命令做 fixture 命中验证时：环境变量 `D9_FIXTURE_PATH` 注入（值为 fixture 文件的绝对路径 `TARGET_PATH/fixtures/<dimension-name>.yaml`，由 `validate_config.py` 从 config.yaml 读 target_path 后拼装）；命令 cwd = TARGET_PATH（与 fixture 所在目录一致——v0.2.1 commit 锁；config-time 与 runtime 行为对齐）。
- signal 命令输出 JSON：`{"total": N, "positive_hit": N, "negative_reject": N}`——total = 跑过的样本数；positive_hit = expect:pass 样本中被判 pass 的数；negative_reject = expect:fail 样本中被判 fail 的数。
- `validate_config.py` 从 fixture 文件自己数 positive/negative 总数，命中率 = positive_hit / positive_total、negative_reject / negative_total。
- 命令未实现 D9 模式（输出不可解析 / 非零退出）→ 该 hard dimension 降级 soft 提示，不阻断（与"不 exit 1 阻断"一致）。
- **不约定入参协议**——命令内部怎么读 fixture / 怎么判定是自己的事（薄骨架，parser 留在命令内）。建议命令用 `pathlib.Path` 读 `D9_FIXTURE_PATH`（不依赖路径分隔符；Windows 下是反斜杠路径）。

### D2 · fixtures/ 目录与格式

- 目录：**统一约定 `TARGET_PATH/fixtures/` 目录**（A 类 Target 仓库根下，随 Target 仓库提交）。协议 Q5 的"同一目录"选项**不在 v0.2 first cut 启用**——first cut 只认 TARGET_PATH 下的 `fixtures/` 子目录，单路径、零 fallback，减少校验分支（v0.2.1 commit 锁）。
- 格式（O1 占位，第一次实跑时定）：`fixtures/<dimension-name>.yaml`，YAML 列表，每条 `{input: <text>, expect: pass|fail}`。
- 80% 阈值（O2 占位）：先写死 80%，第一次实跑后回看。

### D3 · 文本 hard signal 命令模板

- 三段式 `(eval-set-path) + (runner) + (parser)` 全部封装在 `signal` 命令字符串内；`iter.sh` / `validate_config.py` 不理解命令内部结构（薄骨架，parser 不提为骨架件）。
- 退出契约继承 v0.1 D8 rule 6/7：exit 0 + stdout 非空 → 1.0；exit 0 + 空输出 → 0.0（rule 6）；超时 → 0.0（rule 6）；exit ≠ 0 → 当次 reject（rule 7）。
- parser 错误无第三态：malformed stdout 在命令退出 0 时按 rule 6/7 现有语义处理（O3 已定稿）。
- **Signal token 化约定（v0.2.1 commit 锁）**：`signal` 字段作为 `iter.sh:94` 的 `bash -c "$signal"` 参数整体传入，bash 在执行 `$signal` 前会按 IFS 重新词法解析——含未转义空格的命令路径（如 `/opt/my tools/check.sh`）会被错误拆词，第一个 token 当命令 → rc=127 → 走 rule 7 reject。**临时缓解三选项**（v0.2.1 first cut 不预留 stub，c 是已决缓议）：
  - (a) **staging 短路径**：把 d9 runner / hard signal 脚本拷到无空格短路径（如 `C:/Users/.../Temp/d9/d9_runner.sh`）——T4 e2e 测试当前的应对模式。
  - (b) **`python -c "<单引号脚本>"` 包装**：把多 token 命令包成单 token——适合"用 Python 粘合多步"的场景。
  - (c) **iter.sh 用 array 形式 `bash -c "${signal[@]}"`**：让 bash 不重新词法解析——**v0.3+ 再实施，v0.2.1 first cut 不做**（已决缓议，与"薄骨架"纪律一致：不理解 signal 内部 → 不主动重构 token 化）。

### D4 · meta 两维 hard（scripts/meta_check.sh，已落）

- 维度 1：ADR 模板完整度——`docs/adr/ADR-*.md` 必含核心 3 段（背景 / 决策 / 后果）+ 顶部元数据（`**状态**：` / `**关联**：`）；标准 ADR 另含"备选方案（被否决）"，差异表（`KNOWN_ADR_EXEMPT`）可豁免。**差异表 key = 文件 basename（含 .md 后缀）**；维护原则：差异超过 2~3 条 = 重新审视 ADR 模板定义本身。
- 维度 2：模板占位符替换成功率——零 hardcode：模板 grep 提取占位符非空 = OK；运行时产物无 `{{...}}` 残留 = OK（有残留 = 真替换失败，error）。**运行时产物显式列举两个已落文件**：`state/program.md` 与 `state/judge-prompt.md`（与 meta_check.sh 硬编码一致）；新增 state 产物时需同步脚本。
- 替换逻辑出处：`iter.sh:63-72`（program.md 替换）+ `iter.sh:147-156`（judge-prompt.md 替换）——meta_check 不调用 iter.sh，只验证其产物。
- 接口：`--json`（机器消费）/ `--strict`（warning 升级 error）/ 默认 warning 不阻断；**退出码：0 = PASS、1 = FAIL、2 = usage error（参数错）**。
- state 缺失 = warning 不阻断（首次跑 / 空 checkout 不失败）。
- 复用 v0.1 已落件：tests/test_templates.py 占位符集合（pytest 侧权威，脚本不调用）、iter.sh 生成的 state/*.md。
- 模板集边界：`templates/` 当前只有 2 个模板（program.md.template / judge-prompt.md.template）；ADR-004 提到的 scoring.yaml.template 属 meta 第三维资产，**v0.3 再补，v0.2 first cut 不列入**。

### D5 · 扩展 3 件接口规格（只定义，不实现）

以 ADR-005 决策 1 trigger 矩阵为输入（**"不上车的反例"列同 ADR-005 决策 1 表**，本 spec 不重复）：

- **Worktrees**：触发 = 单 writer 串行不够 + 并行分支共享 Target 路径会冲突；接口规格 = per-branch worktree 的 Target 路径映射与 ratchet 同步（v0.2 只写接口规格，不实现）。
- **Plugins**：触发 = 需要外部 hook / adapter 且配置化满足不了变化频率；接口规格 = signal 命令外部化 / provider 适配层（v0.2 只写接口规格）。
- **Sub-agents 派发**：触发 = coordinator 派生子 agent 且需分工 + 状态共享；接口规格 = coordinator program 模板 + 子 agent 结果聚合进 ratchet（v0.2 只写接口规格）。

> **接口规格定义（v0.2 first cut 完成度判据补）**：
>
> "接口规格 / 对外契约"在 D5 语境下指扩展件上车时**实现层对其他组件暴露的契约**，用四元组描述：
>
> - **输入**：组件接收的参数 / 配置 / 触发条件（与 ADR-005 决策 1 trigger 矩阵的"何时上车"列对齐）
> - **输出**：组件产出的副作用 / 数据 / 状态变更（对 ratchet / state / results.tsv 的可见影响）
> - **状态**：组件持久化的中间态（哪些 state 目录文件被读写、是否独立 git ratchet）
> - **依赖**：组件对骨架其他件的复用（signal 命令外部化是否复用 D3 三段式 / ratchet 同步是否复用 ADR-002）
>
> **v0.2 first cut 完成度判据（必备三项，缺一不算"接口规格已写"）**：
>
> 1. **trigger 已落 ADR**——扩展件上车的触发条件已在 ADR-005 决策 1 拍板（"何时上车"列）
> 2. **触发后语义在本 spec 有描述**——本 D5 段给出"触发 = ... → 接口规格 = ..."的一句话契约（输入 / 输出各一句足够）
> 3. **接口字段层留口**——具体参数 schema / 调用协议 / 错误码**不**在 v0.2 first cut 写，v0.3+ 撞 trigger 时再补
>
> **与 D1 的边界**：
>
> - **D1** = hard signal **准入门规则**——对象是 dimension，断言是 fixture-set 命中（≥20 条 + ≥80% 命中）
> - **D5** = 扩展件**对外契约**——对象是组件，断言是接口四元组覆盖
>
> 两者正交：D1 约束 dimension 怎么算 hard；D5 约束扩展件上车怎么搭。

A 类目标域必不装三件（v0.1 spec Out of Scope #2 纪律延续：不为扩展件预留 stub）。

## Testing Decisions

- **测试原则**：只测外部行为。`validate_config.py` 的 D9 校验行为（缺 fixture-set → 提示降级；fixture-set 不达阈值 → 提示降级；通过 → 放行），不测内部实现。
- **T1 · validate_config.py D9 校验**（pytest 单元测，P0；优先级理由：D9 是 v0.2 first cut 的启动门，且覆盖两条独立阈值）。**职责边界：T1 只测 D9 决策分支（缺 / 不达标 / 通过 / 豁免），YAML 解析错误归 T2**：
  - (a) hard dimension 缺 fixture-set → 提示降级且 exit 非阻断（参照 v0.1 T2 的配置校验测试风格）
  - (b) fixture-set 存在但 < 20 条 → 提示降级
  - (c) fixture-set 达标（数量 + 命中）→ 放行
  - (d) fixture-set 数量达标但命中 <80% → 提示降级（执行门槛独立判定）
  - (e) fixture-set 数量 + 命中均达标 → 放行
  - (f) 豁免分支：`pytest -q` 等 KNOWN_EXEMPT 社区共识命令 → 跳过验证放行
- **T2 · fixture-set 格式解析**（pytest 单元测，P1）：`fixtures/<dimension-name>.yaml` 的解析——非法 YAML / 缺 expect 字段 / positive-negative 比例不足，各自报错行为。
- **T3 · meta_check.sh**（shell 集成测，P0）：meta_check.sh 是 v0.2 新脚本，**无 v0.1 prior art，需新写测试**（方法论参考 v0.1 T2 的 shell 集成测试风格）：
  - (a) 正常态 PASS（当前 5 份 ADR + 模板 + state 全过）
  - (b) 删 ADR 段 → 维度 1 FAIL，exit 1
  - (c) state 残留占位符 → 维度 2 FAIL，exit 1
  - (d) --json 输出结构正确
  - (e) --strict 行为（warning 升级 error）
  - (f) state 缺失 → warning 不阻断
  - (g) KNOWN_ADR_EXEMPT 豁免机制：临时把 ADR-005 加入豁免 → PASS；把 ADR-003.5 移出豁免 → FAIL
- **T4 · 端到端：文本 Target demo**（shell 集成测，**P0**；**状态**：闭环 commit `9a04a17` 已落，1 坏 + 2 好模式 3 轮跑通，T4 P1→P0 升级完成）：v0.2 用假文本 Target（一个 SKILL.md + fixture-set）跑 3 轮 loop，具体断言（对照 v0.1 T4 的断言风格）：
  - (i) `state/results.tsv` 行数 = accepted 轮数（仅记 accepted，D8 rule 8）
  - (ii) ≥1 轮 signal 命令 exit ≠ 0 → reject，该轮不入 results.tsv（D8 rule 7）
  - (iii) D9 门在 config-time 跑过（validate_config.py 对文本 Target 的 hard dimension 通过/提示降级行为符合配置预期）

## Out of Scope

- 明确缓议 4 项（D7）。
- Glossary 静态化方案（ADR-004 Open Issue，等 meta 两维 hard 跑出首批数据后单独 ADR）。
- C 类真实 Target 实际上车（v0.2 只做上车评估 + 接口定义，实例化留给 v0.3）。
- CI 接入（meta_check.sh 独立可用，CI 是后续工程节奏）。
