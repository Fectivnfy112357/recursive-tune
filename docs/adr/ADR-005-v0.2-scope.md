## 决策

### 决策 1 · 扩展 3 件 trigger 矩阵

| 扩展件 | 何时上车（触发条件） | 不上车的反例 |
|---|---|---|
| **Worktrees** | 单 writer 串行不够，需要并行分支探索；**且**并行分支间共享 Target 路径会冲突 | 单 writer 串行已够的 A 类场景（v0.1 spec D4 明确不装） |
| **Plugins** | 需要外部 hook / adapter 接入（如 provider 切换、第三方 API 包装）；**且**配置化（直接换配置）满足不了变化频率 | 用 `config.yaml` 直接换配置能满足的场景 |
| **Sub-agents 派发** | coordinator 派生子 agent 协同工作（多 agent 流水线）；**且**子 agent 间需要明确分工 + 状态共享 | 只需 writer / judge 两个 profile 的 A 类场景（v0.1 spec D1） |

> **决策口径**：三件**C 类必装**是事实（use-case 沉淀已落）；trigger 矩阵是"何时必装 vs 何时选装"的判定依据——A 类必不装、C 类必装、C 类下哪个扩展件"该先上"按 trigger 命中数排。

## 备选方案（被否决）

| 备选 | 否决理由 |
|---|---|
| 不写 ADR-005，把 trigger 矩阵留在 use-case 沉淀里 | use-case 沉淀（C 类上车材料）是探索域（ADR-004 §关联 §非 ADR）；触发条件是从 use-case 抽出的"已决判定"，性质是 ADR；两者必须分开，避免 use-case 段被误读为已签发决策 |
| 把 trigger 矩阵写进 ADR-001 | ADR-001 决策的是"全集 vs 实例化机制"（核心 4 + 扩展 3 的归位）；trigger 矩阵是 v0.2-specific 判定，不应污染 ADR-001 的通用接口定义 |
| 把 5 周排期直接写进本 ADR 的"决策"段 | 排期是工程节奏，不是架构决策；放"决策"段会模糊 ADR 与项目管理文档的边界；具体排期挪至 `docs/handoff/v0.2-5week-plan.md` |

## 后果

- **v0.2 spec 起草时**必须引用本文档决策 1（trigger 矩阵）+ 决策 2（已落 commit 索引）
- **use-case 沉淀（C 类上车材料）**作为本 ADR 决策 1 的输入材料；未来 C 类真实 Target 上车时如 trigger 命中，**本 ADR 不需要重写**——只需在对应 use-case 沉淀里加新触发场景
- **明确缓议段的 4 项**不在 v0.2 first cut 范围；v0.2 spec 写 D9 rule 时不要为这 4 项预留任何 stub（spec D4 的纪律——不为扩展件预留空壳结构）
- **`meta_check.sh` 的 `KNOWN_ADR_EXEMPT` 表**（当前 1 条：ADR-003.5）纳入 meta 维护纪律；超过 2~3 条 = 重新审视 ADR 模板定义本身（脚本注释 + 协议已写）
- **D8 rule 12（meta 不阻塞 v0.1 first cut）**升级为 v0.2 同源守护：meta 在 v0.2 first cut 只跑两维 hard，不强求 Glossary 维度——避免 v0.2 implem agent 为凑 meta Score 拖慢 A 类交付
